# Работа в репозитории

## Участники

Владелец определяет продуктовую механику и принимает установленный результат.
Основной архитектор отвечает за общую спецификацию, границы, перенос и объединение.
После отдельного переноса серверный Codex развивает сервер параллельно. Его текущая задача ограничена назначенными доменами; общий контракт не меняется односторонне.

## Одна задача

До правки: прочитать AGENTS, STATUS, ROADMAP, нужную норму и исходный принятый код.
Зафиксировать цель, requirement IDs, исходный commit, область файлов, acceptance scenario, запреты текущего этапа.
Реализовать минимальную законченную часть пользовательского сценария, проверить подходящими средствами, показать результат и ограничения.
Изменения поведения, перемещение кода и обновление зависимостей разделять на обозримые commits/PR.
Не требовать от владельца выбирать библиотеку или SQL-индекс; такие решения исполнитель принимает по существующему стеку и измеримым требованиям.

## Параллельная работа

| Область | Основной ответственный на этапе объединения |
|---|---|
| extension, bridge-core, marketplaces, AI/browser adapters | Архитектор объединения |
| apps/api/portal/admin/worker/health-runner, packages/server | Серверный Codex после переноса |
| packages/contracts, общая auth/синхронизация | Один назначенный автор изменения, review второй стороны |
| product/architecture/decisions | Архитектор; серверный Codex обновляет факты своей реализации |
| STATUS и release manifest | Завершающий этап исполнитель, с указанием точных доказательств |

Не редактировать один файл одновременно. Перед взятием задачи сверить актуальный main и выполняемую работу.
Использовать короткие ветки и небольшие PR. При конфликтах сохранять оба действующих требования, не выбирать ours/theirs вслепую.
Общий runtime не копируется в две вечные ветки. Старые временные import/reference каталоги имеют условие удаления.

## Приёмка изменения

Описание: проблема → что изменилось → фактическое поведение → проверка → ограничения.
Тестовые числа привязаны к коммиту, среде и списку test IDs; повтор того же набора на ZIP не считается удвоением покрытия.
Документация не должна опережать готовность: SPEC описывает цель; STATUS — доказанный факт.
«Файл создан» не равно «функция реализована», «source PASS» не равно «installed PASS», «сервер CI PASS» не равно «развёрнут и подключён к реальному расширению».

После достаточной проверки заканчивать задачу; не создавать дополнительные проходы ради числа тестов.
При выходе owner FAIL заново открывается соответствующий gate и фиксируется воспроизведение. Исторические PASS не стираются и не отменяют FAIL.

## Правила GitHub

Обычный fast-forward/PR merge; без force update общей истории. Перед публикацией повторно проверить HEAD.
Все файлы законченной задачи подготовить и проверить до изменения main. Шаблоны PR/issue поддерживают единый порядок.
Доступы GitHub, защита ветки и окружений проверяются при эксплуатационной подготовке; наличие документа не означает настроенную branch protection.
Отдельного устного подтверждения для уже порученной обратимой задачи не запрашивать. Production release выполняется в рамках соответствующего поручения и готового reviewable кандидата, без выдуманной дополнительной церемонии.
