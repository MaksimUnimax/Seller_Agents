# Архитектура сервиса

Цель: одно расширение и один модульный сервер. Микросервисы, Kubernetes, отдельный брокер и Redis не вводятся без измеренной необходимости.

## Два независимых потока

Основной: страница ИИ → content adapter → локальный worker → marketplace adapter → API площадки → локальный буфер → AI adapter → тот же диалог.
Служебный: control-client → API Seller Agents → PostgreSQL; сюда относятся вход, конфигурация, сведения о магазинах, редкое согласование и безопасная диагностика.
Обычный бизнес-запрос и его результат через сервер Seller Agents не проходят.

## Расширение

| Модуль | Ответственность | Не владеет |
|---|---|---|
| apps/extension | Сборка, popup, lifecycle браузерного процесса, соединение модулей | Бизнес-семантикой API внутри UI |
| bridge-core | Work/session, разбор пакета, локальная очередь, исполнение, доставка, recovery, локальные лимиты через provider policy | Ozon/WB endpoint facts, DOM конкретного ИИ |
| marketplaces/ozon и wildberries | Registry, схемы, auth, хосты, семантика read-only, provider policies | Popup, DOM ИИ, платёжная политика |
| ai-adapters | Идентичность диалога, обнаружение команд, composer/send/attachment proof, capability | Ключи маркетплейсов |
| browser-platform | Storage, alarms, messages, tabs, files, различия manifest/platform | Продуктовая привязка и API магазина |
| control-client | Device auth, refresh, подписанный bootstrap, отложенное согласование/телеметрия | Выполнение команды и содержимое отчёта |

Core зависит от узких портов, а приложения подключают реализации. Нельзя заставлять bridge-core импортировать конкретный маркетплейс или серверную БД.
Секреты и бизнес-запросы доступны привилегированному worker; content script получает только необходимый результат и проверяемые служебные сообщения.
При пробуждении worker состояние восстанавливается из локального хранилища. Постоянная жизнь background-процесса не предполагается.

## Сервер

| Приложение | Роль |
|---|---|
| api | HTTP API аккаунтов, доступа, магазинов и конфигурации |
| portal | Пользовательский сайт, вход, активация, установки |
| admin | Административный интерфейс с отдельной сессией/RBAC |
| worker | Ограниченные фоновые задания, email, агрегации и эксплуатационные задачи |
| health-runner | Изолированные браузерные проверки тестовых AI-аккаунтов |

Это процессы одного продукта с общими типизированными контрактами и модульными доменами, а не пять независимо проектируемых микросервисов.
Текущие серверные пакеты переносятся с сохранением логических имён в packages/server. Доменные изменения идут через их публичные интерфейсы, не через произвольные SQL-записи соседнего приложения.
PostgreSQL хранит учётные данные сервиса и операционные метаданные. Health browser runner изолирован по ресурсам от API.

## Техническая основа

Сохраняем source baseline: Node.js 24, pnpm 10.34.5, TypeScript, Fastify, PostgreSQL, существующие Next/React приложения сервера.
Точные зависимости и lockfile переносим из принятого источника, проверяя пути workspace; обновление зависимостей не смешиваем с перемещением кода.
Новые браузерные границы вводятся постепенно вокруг проверенного JavaScript runtime. Массовое переписывание на TypeScript ради каркаса не требуется.

В D0 отсутствует production-код и приложения не запускаются. Работает только проверка документации.
Порты и API ниже — целевые контракты; schema implementation создаётся на этапе переноса/интеграции.
