# План переноса и объединения

D0 создаёт каркас и документацию. Код источников в этом этапе не переносится.
D1 и далее — отдельное поручение после отчёта владельцу. Исполнитель переноса и объединения: основной архитектор.

## D1. Зафиксировать и перенести

1. Снять свежий HEAD всех трёх веток и текущую authority; сравнить с [SOURCES](SOURCES.md).
2. Определить канонический source/package каждого компонента, зрелые subsystem donors и список известных FAIL/NOT_TESTED.
3. Составить manifest по файлам и oldPath → newPath; включить реальные workspace dependencies, migrations, tests и полезное evidence.
4. Перенести сервер в apps + packages/server, общие wire contracts в packages/contracts. Сначала минимальные изменения путей, без перепроектирования принятых доменов.
5. Перенести выбранный Ozon runtime и WB provider boundary с явной картой частей общего ядра. Непринятый WB можно временно держать reference вне production graph.
6. Сохранить исходные проверки и воспроизводимую сборку. Установить реальные зависимости, создать корневой lockfile принятой версией pnpm.
7. Проверить, что перемещение не поменяло business semantics; опубликовать evidence и handoff для серверного Codex.

Не переносить весь Blood & Sand, старые маркетинговые материалы и все исторические ZIP.
Не начинать параллельную правку сервера до окончания его базового переноса: это создаст лишние конфликты путей.

## D2. Общее расширение

Для подсистемы сравнить последнюю принятую mature Ozon реализацию с WB:
KEEP proven equivalent / PORT complete subsystem / ADAPT provider boundary / EXCLUDE Ozon business / HOLD evidence missing.
Учитывать dependency closure: popup → Work messages → worker states → storage → AI delivery. Нельзя объявить popup перенесённым по одному CSS файлу.
Сохранить доказанно корректные блоки; неполные довести целиком. Не переписывать WB с нуля.

Извлекать общее ядро по вертикальным сценариям: Start → распознавание блока → локальное выполнение → доставка → Finish/recovery.
После первого общего прохода добавить выбор площадки/магазина и неизменяемый контекст пакета. Проверять прежний Ozon после каждого извлечения.
Не импортировать бизнес-сущности Ozon в WB. Не создавать два runtime с одинаковыми ошибками.
WB provider-neutral installed gate открывается только реальной проверкой исправленной сборки. R1–R8 до этого закрыты.

## S1. Параллельный серверный Codex

Передать: exact import commit, package mapping, действующие контракты, список принятых source tests, SPEC/BETA_ADMISSION/SYNC и следующие задачи:
- явный бесплатный BETA access, без зависимости от fake checkout;
- атомарный admission cap + админка;
- реальные email/device/bootstrap в препроде;
- store metadata и необходимые contract additions;
- optional reconcile, перенос и безопасные агрегаты отдельными ограниченными задачами;
- эксплуатационная подготовка и развитие существующего Health после раннего I1.

Сохранять принятые billing/domain модули для будущего, но не показывать их как работающую монетизацию беты.
Новый общий contract меняет один назначенный автор; вторая сторона обновляется по версии.

## I1. Подключить настоящий клиент рано

Минимальный сценарий: портал OTP → активация установленного расширения → signed bootstrap → выбранный магазин → явный пакет → реальный разрешённый ответ → доставка в ИИ.
Отключить control plane и подтвердить работу в пределах signed grace без запроса на каждый пакет.
Не ждать полного администрирования, payment integration или всех monitor dashboards.
Сначала один безопасный принятый сценарий, затем другие источники/магазины/браузеры и редкие случаи по матрице.

## Q1/B1

Препрод, final package, installed evidence, rollback/restore, минимальный сайт.
На beta production регистрации закрыты, пока владелец не откроет начальную квоту.
После отчёта и фактической готовности публикуются принятые browser targets, остальные честно обозначаются по статусу.
Возможность подготовить Safari package не заменяет реальный Mac gate.

## Квитанция этапа

Входные коммиты → перенесённые файлы → намеренные изменения → сохранённые/новые проверки → package/hash → failed/not-run → текущий STATUS → следующий ограниченный шаг.
Блокер одного subsystem не маскируется общим процентом готовности.
