# Контроль DOM и API

Мониторы проектируются сейчас; расписания, боты и production задачи в D0 не создаются.
Используем существующий серверный health-runner как основу, не дублируем его новым независимым сервисом.

## DOM Health

Технический стартовый режим: один поведенческий проход в сутки по принятым AI targets; лёгкое структурное наблюдение до нескольких раз в сутки при необходимости и допустимости доступа.
Расписание, аккаунты, бюджет и target matrix включаются только после приёмки runner. Недоступность модели/капча не обходятся.
Тестовые аккаунты отдельные; токены/диалоги клиентов не используются.

Проверяем: trusted origin/account, идентичность нового/существующего диалога, composer, распознавание блока, вставку, доказательство отправки, readiness файла и восстановление после DOM replacement.
Структурный diff служит сигналом; невидимое изменение DOM без потери поведения не равно поломке.
HEALTHY, DRIFT, DEGRADED, BROKEN, UNKNOWN, MAINTENANCE различаются. Ошибка входа/сети/runner — UNKNOWN или отдельный операционный инцидент, не доказательство глобально сломанного AI adapter.

Сигнал содержит target/browser/version, время, последнее успешное наблюдение, очищенный structural diff, упавший сценарий и candidate scope.
Специалист воспроизводит, определяет профиль vs packaged-code change, готовит patch и проходит [путь выпуска](RELEASE_AND_RECOVERY.md).
Простой watcher не получает права публиковать production код или расширять команды.

## API watcher

Ежедневно проверяет официальные OpenAPI/Swagger и changelog известных площадок; conditional fetch при поддержке, ограниченные повторы только загрузки спецификаций.
Недоступная спецификация = FETCH_UNKNOWN. Не заменять её пустым inventory и не объявлять все endpoints удалёнными.
Изменение подтверждается хешем и нормализованным semantic diff, включая shared schemas, auth, response, privacy, limits, deprecation/effective date.

Обязательная инструкция классификации: [READ_POLICY](../integrations/READ_POLICY.md). Для каждой строки сохраняются источник и решение; HOLD видим.
Выход: candidate diff registry/HELP/schemas + human-readable причины + новые/изменённые fixtures. Никаких автоматических бизнес-вызовов или auto-enable.
WB R1–R8 gate действует также на задания watcher: обнаружить изменение документации можно, начинать реальную характеристику закрытых групп нельзя.

## Доставка сигналов и нагрузка

В бете достаточно одной очереди уведомлений в админке/issue candidate и выбранного владельцем канала. Публикация сообщений третьим лицам требует соответствующего поручения; здесь каналы не включаются.
Одинаковые сигналы дедуплицируются; recovery закрывает инцидент; нет тысячи одинаковых уведомлений при падении одного сайта.
Browser runner имеет ограниченную параллельность, timeout и отдельный ресурсный лимит. Он не забирает все DB connections/API workers.
Оператор видит последнее успешное выполнение самого монитора: отсутствие уведомлений при сломанном runner не трактуется как здоровье.
