# Среды, выпуск и восстановление

## Среды

| Среда | Назначение | Данные и доступ |
|---|---|---|
| Local/CI | Быстрые воспроизводимые проверки и disposable PostgreSQL | Fixtures, тестовые секреты, без клиентов |
| Preprod | Установленный кандидат + настоящий тестовый сервер/почта/AI контур | Отдельные БД, домены, sessions, signing keys и тестовые аккаунты |
| Production beta | Бесплатные реальные пользователи с регистрационной квотой | Production эксплуатация и контролируемое открытие набора |

Нельзя использовать одну БД или signing key для препрода и production. Health runner и большой файл не должны вытеснять рабочий API по CPU/RAM/pool.
Клиентские токены не требуются для обычного CI. Реальные read-запросы допускаются только в соответствующей назначенной приёмке.

## Путь патча

1. Изменение и нужный regression в короткой ветке.
2. CI по действующему коду и зависимым контрактам.
3. Candidate package и manifest, установка на препроде.
4. Проверка изменённого поведения и критического общего пути.
5. Подготовка финальных browser packages, хеши и проверки именно их окружения/конфигурации.
6. Выпуск в рамках порученного этапа; небольшой rollout где канал это поддерживает, затем расширение.
7. Проверка после выпуска, наблюдение ошибок, pause/rollback при подтверждённой проблеме.

Preprod package с другим extension ID/domain не является побайтово тем же production package. Final evidence относится к фактическим финальным байтам.
Dev/test autorun не входит в beta bundle. Версия пакета меняется при изменении поставляемых байтов; одинаковый номер для существенно разных релизов недопустим.
Расширение распространяется поддерживаемым каналом браузера; серверные профили не скачивают исполняемый патч мимо правил магазина.

## Минимальная готовность production beta

Рабочие HTTPS/домен, реальная отправка OTP, отдельные secrets, закрытые административные endpoints, журнал аудита и усиленный admin вход.
Ограниченные логи, метрики ошибок/latency/DB, понятный канал связи пользователя.
Автоматический backup БД и проверенное восстановление на изолированной среде. Начальная эксплуатационная цель: ежедневный backup, хранение 7 дней, RPO до 24 ч, целевой RTO до 4 ч; фактическую достижимость подтвердить репетицией.
Backup не содержит ключей площадок и отчётов, потому что они не должны попадать в БД.
Квота набора первоначально закрыта; владелец явно открывает число мест.

## Rollback

Профиль: вернуться к совместимой принятой ревизии без изменения локального allowlist.
API: вернуть предыдущий образ при совместимой схеме; учитывать незавершённые jobs/idempotency.
DB: expand/contract; не выполнять автоматический destructive down ради rollback. При необходимости restore/forward-fix с указанной потерей данных.
Расширение: rollback зависит от канала обновления; обычно нужен новый совместимый выпуск с повышенной версией. Не обещать мгновенный downgrade всех установок.
Устройства со старым клиентом получают совместимый signed policy и ясный UPDATE_REQUIRED только при реальной необходимости.

## Инцидент

Определить affected browser/AI/version/operation, проверить evidence, ограничить конкретную проблемную возможность.
Не отключать все маркетплейсы из-за одной ошибки DOM или одного health UNKNOWN.
Зафиксировать время/воздействие/решение/проверку восстановления. Постмортем краткий, конкретная защита добавляется в FAILURE_LEDGER и regression.
